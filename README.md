# compressor.benchmark

Сравнение компрессоров при упаковке одного и того же набора файлов через `tar`:
замеряем **время сжатия**, **размер** архива и **скорость распаковки**.

Сравниваются: `gzip`, `pigz`, `xz`, `zstd` (уровни 3, 6, 9, 12) и `lz4`.
Плюс baseline — обычный `tar` без сжатия: он показывает «пол» по дисковой подсистеме
(сколько занимает сам проход по данным), с которым надо сравнивать остальные строки.

## Требования

- `tar`, `gzip`, `pigz`, `xz`, `zstd`, `lz4`, `curl`
- `tar` должен уметь `-a` (автовыбор кодека по расширению) и `-I`
  (`--use-compress-program`)

## Подготовка данных

Скачивает `openIDE` (~3.1G после распаковки, 2293 файла) и раскладывает его в `.data/`:

```sh
bash ./prepare_data.sh
```

Скрипт скачивает архив, распаковывает в `.data`, убирает лишний вложенный каталог
и удаляет скачанный `.tar.gz`.

## Запуск бенчмарка

```sh
bash ./bench.sh
```

`bench.sh` сначала жмёт набор архивов (baseline `tar` без сжатия + пять «дефолтных»:
`gzip`, `pigz`, `xz`, `zstd`, `lz4` + `zstd` на уровнях 3/6/9/12), затем распаковывает
их двумя способами: на диск и «в поток» (`/dev/null`, чтобы исключить запись на диск и
увидеть чистую скорость кодека).

Число потоков нигде явно не задаётся — инструменты используют свои дефолты (см. ниже).

| Команда | Что это |
|---|---|
| `tar -cf archive.tar -C .data .` | baseline: обычный `tar` без сжатия (чистое I/O) |
| `tar -caf archive.tar.gz -C .data .` | gzip, дефолт (уровень 6) |
| `tar -I pigz -cf archive.pigz.tar.gz -C .data .` | pigz, дефолт (уровень 6) |
| `tar -caf archive.tar.xz -C .data .` | xz, дефолт (уровень 6) |
| `tar -caf archive.tar.zst -C .data .` | zstd, дефолт (уровень 3) |
| `tar -I lz4 -cf archive.tar.lz4 -C .data .` | lz4, дефолт (уровень 1) |
| `tar -I 'zstd -6'  -cf archive.6.tar.zst  -C .data .` | zstd, уровень 6 |
| `tar -I 'zstd -9'  -cf archive.9.tar.zst  -C .data .` | zstd, уровень 9 |
| `tar -I 'zstd -12' -cf archive.12.tar.zst -C .data .` | zstd, уровень 12 |

## Настройки по умолчанию

Что инструменты используют, если параметры не задавать (проверено на установленных
версиях):

| Инструмент | Уровень по умолчанию | Потоки по умолчанию |
|---|---|---|
| gzip | `-6` | нет многопоточности |
| pigz | `-6` | все ядра |
| xz | `-6` | `0` = все ядра (xz 5.8.3) |
| zstd | `-3` | эвристика `max(1, min(4, nbCores/4))` → здесь `4` |
| lz4 | `-1` | нет (этот билд однопоточный) |

На этой машине 16 логических ядер (8 физических), поэтому «все ядра» в таблице = 16 потоков.

Baseline — это не компрессор (обычный `tar` без кодека), у него нет ни уровня, ни потоков;
он нужен только как точка отсчёта по скорости диска.

## Результаты

Данные: `.data` = 3.1G, 2293 файла.

## Выводы

**Baseline задаёт масштаб.** Сам `tar` без сжатия записывает 3.1G за ~4 с, читает «в
поток» за ~2.4 с и распаковывает на диск за ~5.5 с. Отсюда видно, почему распаковка на
диск у всех кодеков скучилась в 8–14 с: часть этого времени — неизбежное I/O, а не работа
кодека. На «чистом» потоке разрыв между кодеками проявляется уже ярче (2.4 с baseline против
3.4–10.4 с у остальных).

**По скорости `zstd` категорически выигрывает на дефолте.** `zstd` по умолчанию
(`-3`) жмёт за ~7.7 с: это ~11 раз быстрее дефолтного `gzip` (~83 с) и
~22 раза быстрее дефолтного `xz` (~2 м 47 с), причём **меньше** `gzip` на ~5%.
Это лучший баланс «скорость + размер» из всего набора.

**Увеличение степени сжатия почти не уменьшает размер.** От `zstd -3` к `zstd -12`
архив уменьшается всего на ~108.6 МБ (~8.7%), при этом время растёт в ~9 раз
(7.4 с → 65 с). Шаг `-9 → -12` даёт вообще −9.6 МБ (~0.8%) за +29 с. Гнаться за
максимальной степенью сжатия смысла мало.

**`pigz` оправдывает себя только как «многопоточный gzip»** (83 с → 13 с при том же
размере), но всё равно проигрывает `zstd` и по скорости (13 с против 7.7 с), и по
размеру. То есть `pigz` для `gzip` — это то, что `zstd` и так умеет из коробки.

**Если нужен именно формат `.gz` (совместимость), `pigz` имеет преимущество.** Он выдаёт
**тот же стандартный gzip-поток** (`.gz`), который распакует любой `gzip`/`tar`/`7-Zip`,
но сжимает в ~6.5 раз быстрее обычного `gzip` за счёт многопоточности — то есть
ускоряет без потери совместимости. Минус: распаковка у него по-прежнему однопоточная
(как у `gzip`).

**`lz4` — край по скорости, но самый большой архив** (1.6G — больше `gzip`). При этом
дефолтный `zstd` жмёт с той же скоростью (~8 с) и даёт на ~430 МБ меньше, поэтому
`lz4` в этом сценарии смысла не имеет.

**`xz` — самый маленький архив** (980 МБ), но за счёт времени: ~2 м 47 с на сжатие.

**Распаковка: `zstd` — самый быстрый** (3.4 с в поток), `xz` близко (4.6 с,
но раскодирует в несколько потоков), а `gzip`/`pigz` самые медленные (~9–10.4 с).
При распаковке **на диск** разница сглаживается: всё упирается в запись 3.1G (большинство
~8–14 с), так что в реальной распаковке скорость диска важнее кодека.

### Итог

> **`zstd` (дефолт) — лучший выбор по совокупности скорости и размера.**
> Остальное — под конкретную задачу.

| Приоритет | Выбор |
|---|---|
| Лучший баланс | **`zstd` (дефолт, `-3`)** |
| Минимальный размер | `xz -6` (или `zstd -9/-12`, если время не важно) |
| Обязателен формат `.gz` | **`pigz`** (совместим с `gzip`, и в ~6.5 раз превосходит его по скорости) |
| Максимум скорости сжатия (ценой размера) | `lz4` (но `zstd` жмёт так же быстро и меньше) |

### Оговорка

`gzip` однопоточный, `pigz`/`xz`/`zstd` — многопоточные, `lz4` в этом билде
однопоточный, поэтому сравнение по времени отражает настройки «из коробки», а не
однопоточную эквивалентность. Число потоков нигде не задаётся вручную: на этой машине
дефолты (`pigz`/`xz` — все ядра, `zstd` — 4 воркера) оказались быстрее явного `-T0`
(все ядра), который переподписывает CPU и замедляет `zstd`. Строки `zstd` (default) и
`zstd -3` совпали по размеру (и почти по времени) — это один и тот же уровень сжатия.

## Распространённость `zstd` и совместимость

Выбор `zstd` не должен создать проблем пользователям: формат открытый,
стандартизован и поддерживается практически везде.

- **Открытый стандарт.** Формат описан в RFC 8878 (медиатип `application/zstd`,
  расширение `.zst`, HTTP-кодирование `zstd`), есть независимые реализации.
- **Ядро и ФС.** В Linux с версии 4.14 (2017): btrfs, squashfs, zram, сжатие модулей
  ядра; также FreeBSD и OpenZFS (2020).
- **Дистрибутивы.** Пакеты с `zstd` приняты в Debian/Ubuntu (2018) и Fedora RPM
  (2018); по умолчанию — Fedora с 31 (2019), Arch Linux с 2020 (переход xz → zstd),
  следом Ubuntu. `gzip`/`xz` при этом никуда не делись.
- **Браузеры и HTTP.** Chrome 123 и Firefox 126 (2024) поддерживают
  `Content-Encoding: zstd`.
- **ОС.** Windows 11 штатно распаковывает `.zst` (2023).
- **Инструменты.** GNU tar (`--zstd`, с 1.31), rsync (3.2.0, 2020), 7-Zip (21.07+),
  а также `unzstd` / `zstd -d`.
- **СУБД и платформы.** PostgreSQL 16 (`wal_compression = zstd`), Apache Kafka 2.1,
  RocksDB; Python 3.14 добавил zstd в стандартную библиотеку.

Итого: `zstd` есть в любом современном дистрибутиве (ставится одной командой или уже
предустановлен), а распаковать `.tar.zst` умеют и `tar`, и `7-Zip`, и Проводник
Windows 11. Для получателя архива это уже не экзотика.
